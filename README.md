# Coral Club · Реестр инициатив

Прототип веб-приложения для сбора и классификации инициатив руководителей функций
(привязка к проектам компании или к целям стратегических треков), плюс админ-панель
для управления справочниками (проекты, треки/цели/KR, отделы) и просмотра поданных
инициатив.

Всё приложение — один файл `index.html` (HTML + CSS + JS, без сборки, без зависимостей
кроме шрифта Inter с Google Fonts).

## Как открыть локально

Просто откройте `index.html` в браузере — двойным кликом или через
`File → Open`. Ничего устанавливать не нужно.

## Пароли доступа

- `ILoveCoralClub` — режим руководителя функции (заполнение формы инициативы)
- `IamCoralEvo` — режим администратора (редактирование справочников)

Пароли больше не хранятся в коде страницы. Проверка происходит на стороне
Supabase: пароли лежат в таблице `app_auth`, у которой **нет ни одной RLS-
политики** — то есть напрямую прочитать эту таблицу через API нельзя никому,
даже с ключом из `index.html`. Единственный способ проверить пароль — вызвать
Postgres-функцию `check_login(password)`, которая сверяет пароль внутри базы
и возвращает только роль (`lead` / `admin` / ничего) — сам пароль наружу
никогда не уходит.

⚠️ **Тем не менее это всё ещё не полноценная защита от целенаправленной
атаки.** Функция `check_login` доступна публично (иначе браузер не смог бы её
вызвать), и её можно дёргать напрямую через API сколько угодно раз — рейт-
лимита нет, значит теоретически возможен перебор паролей методом brute-force.
Для случайных посетителей и внутреннего использования это ограничение
достаточно, но для полноценной защиты понадобится Supabase Auth с
ограничением частоты запросов.

## Хранение данных

Приложение хранит все данные (проекты, треки, отделы, поданные инициативы) в
**общей базе Supabase** (таблица `app_kv`, простое key-value хранилище: один
ключ = один справочник или список инициатив целиком, в формате JSON).

Это значит:

- Данные **общие** — любой, кто откроет сайт (с любого устройства, браузера,
  IP), видит и пишет в одну и ту же базу.
- Изменения администратора (например, тип проекта) сразу видны руководителям
  функций, и наоборот.
- Ключ Supabase (`publishable key`) прописан прямо в `index.html` — это
  ожидаемо для чисто клиентского приложения без бэкенда, но означает, что
  **любой, кто откроет исходный код страницы, получит этот ключ** и с ним —
  полный доступ на чтение/запись/удаление всей таблицы `app_kv` в обход
  паролей на экране входа (пароли — это просто UI-заглушка, не защита API).
  Это приемлемо для внутреннего прототипа, но для реального использования
  вне контролируемого круга людей стоит подумать над дополнительной защитой
  (Supabase Auth + RLS-политики по пользователю, вместо публичного доступа).

## Деплой на GitHub Pages

1. Создайте новый репозиторий на GitHub и запушите в него этот проект:
   ```bash
   git remote add origin https://github.com/<ваш-аккаунт>/<название-репо>.git
   git branch -M main
   git push -u origin main
   ```
2. В репозитории на GitHub: **Settings → Pages**.
3. В разделе **Build and deployment** выберите **Source: Deploy from a branch**,
   ветку **main**, папку **/ (root)** → **Save**.
4. Через 1–2 минуты сайт будет доступен по адресу вида
   `https://<ваш-аккаунт>.github.io/<название-репо>/`.
